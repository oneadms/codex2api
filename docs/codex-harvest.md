# Mihomo 与采票工作台

管理台侧栏的「采票工作台」统一管理出口、自动采票、网关借票、手动任务和记录。
本次对齐 [sub2api production](https://github.com/ranxi2001/sub2api/tree/16dc0e0165b696d7e418c915e8952c1c859a4dc6)
的采票工作台：多来源/目标账号、Cookie 路由借票（HTTP 与 WebSocket）、780 统一票库快速复用、
固定 WebSocket 会话和票库调度。来源和许可见 [NOTICE](../third_party/sub2api/NOTICE.md)。

## 配置入口

1. 进入「采票工作台 → 票据策略」的 Mihomo 卡片，安装并启动内核，添加 Clash / Mihomo YAML 订阅。
   内核固定为 v1.19.27，从官方发行版下载并验证 SHA-256，支持 Linux amd64 / arm64。
2. 按需配置出口地区、停用节点和「每个节点只用一次」，然后点击「设为采票代理」。
   Windows 服务可使用外部代理；内置内核需要 Linux / Docker。
3. 在「票据策略」启用采票，配置模型（例如 `gpt-6-astra`）和门票目标。
   出厂目标为 **780**，也可选 292、332 或按套餐选择 292 / 332。
   升级后的已有配置以页面显示的目标为准。
4. 在「采票控制」选择采票协议、票据策略和代理管理中的多个启用代理，并配置账号范围后保存。
   所选代理按 `proxy_ids` 列表轮换，串行、自动与并行均实际使用该列表；每个候选的两次请求保持同一代理。
   代理池留空时使用全局采票代理或 Mihomo；被停用、删除或检测失败的代理不会被新候选使用。
   票据策略 `refresh` 在临期前自动备票，`fixed` 保持当前主票直到失效；
   旧版的单来源复用字段不迁移。
   可选公网边缘 IP 只改变连接目的地址，保留原上游 Host、TLS SNI 和证书验证。
5. 在「网关借票」选择来源账号和目标账号。来源和目标都是多选，来源列表只选一个账号就是单来源；
   两组不能重叠。旧版单来源配置不会迁移，升级后需要重新选择并保存；保存前借票保持关闭。
   已选账号从列表消失后仍显示其 ID，可取消选择；保存时会清理本版旧配置中已不存在或不再支持
   Codex 的账号引用，新加入的无效 ID 仍会报错。若清理后缺少来源或目标，借票及固定 WS 会话
   自动停用；其他设置保留。关闭路由 Cookie 池会同时关闭依赖它的固定 WS 会话。

代理 `3101`、控制器 `9098` 和采票通道 `17893–17924` 均监听回环地址，无需映射到公网。
内核、订阅及节点状态保存在 `$DATA_DIR/mihomo-managed`，Docker 默认 `DATA_DIR=/data`。
订阅更新或配置校验失败时保留原配置。管理状态不返回订阅凭据、内核密钥、票体或 Cookie。

## 780 票验收

- 每个自采候选从空 Cookie、空 turn-state 和新会话开始，不继承账号自定义材料或旧票。
- 首次短请求必须完整结束，返回目标模型的合格信封及有效 `__cflb`、`__oailb` Cookie 对。
- 第二次请求使用同出口、同会话和同协议，回带本次候选完整材料。只有完整完成、原票未重签、
  路由 Cookie 对未变化才入库。部分 Cookie 更新不能与旧 Cookie 拼成一对。
- HTTP 200 或 WebSocket 101 本身不代表通过；流错误、缺少完成事件、截断、鉴权和限流均失败。
  探针只要求短回复，不使用工具或模型自报版本判断资格；续接通过不代表质量测试通过。
- 原生 WS 业务需要 WebSocket 协议的票。开启缺票拦截时，只有 SSE 票会返回明确的
  `codex_ticket_unavailable`（503），不会裸请求上游，也不会等到选号超时才报错。
  普通请求仍可在重试预算内尝试其他合格账号；固定会话和已绑定续聊不因此换号。
- 账号列表中明确勾选「跳过采票」的账号不再因缺票被拒绝出站，普通请求和「测试连接」均适用。
  取消跳过后恢复缺票拦截；其他账号继续遵守原有策略，忙碌或冷却不会自动获得豁免。
- 两次请求都计入预算，失败及已经发出后取消的请求也计数。串行路径的 401 刷新后探测重试同样计数。
- 780 票必须保存 `probe_verified` 和协议；缺少标记的旧票不可用。SSE 与 WebSocket 分别采验、分别使用。

292 / 332 目标仍校验信封、长度、时效、Cookie 和成功终态，不执行 780 的第二次续接。
Cookie 有效窗口为 240 秒，并遵守更短的服务器到期时间；票据使用 240 秒本地缓存上限和
30 秒余量。Cookie 内的 JWT 声明只用于判断路由到期，不能作为账号认证或延长票据寿命。

## 网关借票（Cookie 路由）

「网关借票」有两条路径，都在来源和目标分离的前提下工作：来源只提供路由材料，目标始终使用
自己的 OAuth、工作区和新会话。Cookie 与探针票只留在内存，管理接口和历史表不返回票体。

**Cookie 路由式借票（HTTP 与 WebSocket）**：来源先发一次完整成功的短请求，取得 `__oailb`
路由 Cookie，并记录来源身份、出口和节点。目标业务请求沿用这条路由 Cookie 和同一出口，
认证仍用自己的凭据。HTTP 请求在出站头替换 `__oailb`；WebSocket 在握手时携带来源路由 Cookie。
没有可用路由或可选节点租约失败时，不注入来源 Cookie，沿用目标正常业务出口及原有缺票策略。
实际借用时 Cookie 与本次选择的出口绑定，不被 Resin 覆盖；托管 HTTP 节点换路时重新建立连接。

目标验收使用两发探针：第一发取得目标自己的 tickets state，第二发带原 state 和借来的路由续接。
两发都完整成功、续接没有返回新 state（或原样返回）且 `__oailb` 未变化才标记为目标可用。
判据只看门票续接，不看响应自报的模型名。来源代理亲和、托管 Mihomo 节点轮换、节点冷却和
路由有效期都适用于这条路径；路由有效期不因重复使用而延长，过期后重新获取并重新验收。

## 780 快速复用（统一票库）

`gpt-6-astra` 自动采票在 **780 / SSE** 模式下，先尝试一次统一票库中的有效来源票。来源由多选列表
按顺序提供，列表只有一个账号时与单来源行为一致。目标带来源完整材料取得**不同的目标 state**，
再回带目标材料续接。来源原票不会作为目标票入库；最终保存目标自己的票、Cookie、协议、有效期、
来源标记和出口信息。

保存借票配置或显式「准备」可在最多 90 秒内调用同一自采器给来源补票，并遵守来源范围、
跳过标记、忙碌状态和失败冷却。来源选择会考虑更长寿命的备用票，要求至少剩余 30 秒。
自动采票找不到合格来源或普通复用失败时，可按剩余预算转目标自采；目标鉴权失败、取消或落库失败停止。
手动串行及并行始终为目标自采。关闭借票不删除已验收目标票；WS 不借用 SSE 票。

**780 / WebSocket 的路由 Cookie 借用**：适用于采票配置中的所有模型，包括 `gpt-6-astra`、
`gpt-6.1-sol`。目标账号没有请求模型的 WS 票时，可从所选来源账号已验收的**同模型 WS 票**
中提取 `__oailb`，沿用来源出口及节点租约建立连接。只配置其他模型也可使用，不依赖 Astra。
目标仍使用自己的 OAuth 和工作区，不携带来源 turn state、会话或其他 Cookie。
缺票拦截在路由绑定后判定；没有合格来源或出口不可用时，继续按原缺票策略处理。
来源票和 Cookie 的有效期沿用原始时间，不因借用延长；普通请求不触发补采。

普通 WS 和「测试连接」重新握手以发送当前来源 Cookie；固定会话续聊保持原连接。
借路由不会生成目标自己的完整票，因此「当前持票」仍可能显示无票，应以实际请求或 WS 诊断结果判断。
显式「准备」按配置模型检查来源，并共用每轮请求预算；WS 诊断逐个模型验收两轮原连接续聊。

## 固定 WebSocket 会话

启用后按 API Key、客户端会话标识、目标账号、请求模型、账号凭据版本和配置版本隔离。首轮请求建立固定
会话，后续请求必须提供 `previous_response_id`，并回到原 WebSocket 连接；原连接不可用时显式失败，
不会悄悄换连接续接。会话截止时间不会因续接向后滑动。账号身份、凭据、分组或配置变化、
响应失败、连接断开都会使会话失效。该能力默认关闭，只对勾选的账号生效。

固定会话模式下，原连接丢失时明确失败，不经过普通续接的重放恢复。线程和后台请求类型分别隔离，
客户端未提供显式会话／线程时，不使用服务端生成的缓存键冒充客户端身份。成功响应中的 `error: null`
按无错误处理。管理台 WS 诊断通过真实业务执行器完成两轮，在原连接传递 `previous_response_id`。

删除账号不会让它创建的续聊状态变得可移植。HTTP Responses 与原生 WS 在发现原绑定账号已不存在时，
会立即返回上下文不可用并提示新建会话，不再耗尽选号等待时间；原生 WS 的加密历史也不会转发给其他账号。
原账号仍存在但并发已满时，继续遵守原有等待与限额规则。

配置使用独立的 `revision`（每次保存的并发保护）和 `route_revision`（路由／固定会话生命周期）。
仅修改调度不会销毁连接或路由；旧草稿仍必须返回 409，不能用新版本号覆盖别人保存的设置。

## 票库调度

启用后，按采票范围内账号的有效票库存恢复本功能拥有的调度变更；缺票时按设置暂停账号、屏蔽
`gpt-6-astra` 模型或移出指定分组。Cookie 诊断结果不作为调度依据。切换模式先恢复旧动作，遇到人工
编辑冲突不覆盖。关闭接管保留当时状态。仅切换调度设置不会清空路由或固定会话。
由本功能暂停调度的账号仍可继续采票，有效票补齐后自动恢复；人工暂停、硬禁用和健康冷却
仍按各自规则限制采票，不会因为调度接管标记而被放行。

## 串行与并行任务

「手动采票」可设置账号、模型列表、请求间隔、最大请求数、限流等待、节点切换规则和「出票即停」。
不勾选「出票即停」时继续其他模型，每个模型保存首张成功票后跳过。
账号处理业务时等待，每次探测前重新检查范围和采票开关；任务可随时停止。

并行采票可使用已选普通代理池，也可使用运行中的内置 Mihomo。默认 10 路，不再固定限制为 32 路，
手动请求预算也不再限制为 100 次；实际并发受可用代理／节点和剩余预算约束。
Mihomo 每路拥有独立 Selector 与监听端口，超过默认监听数量时分配临时回环端口，避开网关监听范围；
任务结束恢复默认配置，任务内节点只分配一次。普通代理池每个候选固定一条具体代理。
所有通道及模型共用请求预算；780 候选先预留两次额度，按实际请求计数并退回未用额度。
发送前与落库前复核账号身份和出口资格；某模型首张票落库后取消其余在途请求。
鉴权、限流或落库失败停止该账号本轮后续采集，冷却取配置期限与 `Retry-After` 中较长者；
模型的不可重试错误停止该模型，不重复耗尽预算。

自动与手动任务使用同一采集锁。自动采票轮换账号，保持健康主票；临期时才按策略准备备用票，
新候选不会仅为补齐备用而替换健康主票。
「每个节点只用一次」在出站前持久化预留；下一个候选使用新节点，
取消后也不会自动恢复。管理员可手动恢复节点，地区筛选和停用状态持续生效。

## 业务材料与出口

业务使用完整票据快照：state、Cookie、会话、协议和代理绑定。780 票不直接进入旧的同套餐共享池。
托管采票节点可以被业务回选，即使它已经标记为「已使用」；管理员停用、失败、地区排除或节点身份
变化仍会拒绝回选。节点租约保持到响应关闭，避免并发切换出口。

业务响应若重签 780 票或改变路由材料，撤销原票、提升合格备用票并补采，不能继承旧验收标记。
不会为验票而重放已经发送的业务请求。手工注入继续优先；普通轮换代理地址相同不保证出口 IP 相同。

## 定向学习与外部代理

内置 Mihomo 的串行自采可使用托管节点定向与学习。外部 Mihomo 仍需专用 Selector 和 listener；
配置放在 `$DATA_DIR/mihomo-codex/config.yaml`，provider 的本地 YAML 快照也放在该目录。
例如：

```yaml
mixed-port: 3101
allow-lan: false
external-controller: 127.0.0.1:9098
secret: replace-with-a-private-secret
proxy-providers:
  airport:
    type: http
    url: https://example.com/subscription
    path: ./airport.yaml
    interval: 3600
proxy-groups:
  - name: CODEX-HARVEST-SELECT
    type: select
    use: [airport]
listeners:
  - name: codex-harvest-directed
    type: mixed
    listen: 127.0.0.1
    port: 3102
    proxy: CODEX-HARVEST-SELECT
rules:
  - MATCH,CODEX-HARVEST-SELECT
```

外部采票代理设为 `http://127.0.0.1:3102`。启用节点学习后，按账号身份、模型和信封形状记录
节点成功、未命中、错误、延迟与冷却，优先近期成功节点并探索其他节点。定向不可用时页面提示，
普通外部代理按自身轮换规则出站；不能把它视为固定出口。

## 持久化与验证

票据先写数据库再发布，重启恢复完整快照。范围、控制、学习和事件支持 SQLite / PostgreSQL；
重置学习记录会推进版本，旧在途结果不能写回重置前统计。事件保留 7 天，最多约 10,000 条。
任务状态展示实际请求数、HTTP 状态、长度、Cookie 数与结果，不返回敏感材料。

管理状态和历史表只保存账号 ID、网关主机名、结果原因和时间，不保存 Cookie、票体或代理凭据。

本次测试使用离线 HTTP / WebSocket 和 Mihomo 控制器 mock，覆盖双请求验收、协议隔离、来源补采、
共享预算、节点预留、持久化、业务失效与边缘 IP 的 TLS 行为；网关借票覆盖多来源选择、
配置版本冲突、HTTP 路由注入、WebSocket 固定会话原连接续接和配置变化失效。
桌面页面使用 mock 接口验证。当前 Windows 环境未运行真实 Linux Mihomo、PostgreSQL 或真实账号采票；
线上成功率未验证。Docker 镜像工作流包含相关后端、竞态、PostgreSQL 持久化和前端检查。
