# TRAECN Responses 断线恢复

适用于 `Codex → NewAPI → codex2api → TRAECN` 的 HTTP Responses 流式请求。

## 启用网关任务保留

```yaml
TRAECN_RESUME_ENABLED: "1"
TRAECN_RESUME_TTL_SECONDS: "60"
```

默认关闭。修改配置并重新构建、部署后生效。API Key 的上游渠道需要明确选择 TRAECN；自动混合渠道、Chat、Messages、非流式和压缩请求继续使用原流程。

启用后，网关将一次生成与客户端连接分开：

1. 首次请求启动后台任务，沿用原处理流程管理账号并发、用量和完成后的上下文缓存。
2. 生成的完整 Responses 事件立即发给客户端，并保存一份可回放记录。符合续传条件的请求会关闭原“持续重试”的整轮缓存和不确定错误换号重试，恢复实时输出；开始输出前的明确 HTTP 401 和 429 仍按配置换号。
3. 客户端断开后，上游继续运行。保留期内收到匹配的重试请求，就接回同一任务，复用原响应 ID 和输出项 ID，不再占用第二个上游并发位。
4. Codex 回传到 `input` 的已完成消息和推理项，只有 ID 与内容均匹配才被视为已接收；其相关事件不再重放。尚未完成的项从该项开始回放。
5. 最后一个连接断开超过保留期后，网关取消任务并清理缓存。用户主动停止与网络断开无法可靠区分，因此主动停止也可能继续生成至保留期结束。

这不是客户端事件游标协议。网关不把游标写进 `previous_response_id`，也不依赖 Codex 回传 SSE 注释或 `Last-Event-ID`。

## 共享 API Key 下如何关联

- **已有验签通过的 NewAPI 用户身份**：使用平台、用户、网关 Key、线程、轮次、权限范围和请求内容关联。NewAPI 每次重试生成新的请求 ID 也可以接回。线程、轮次标识须稳定透传。
- **只有 `X-NewAPI-Request-ID`**：仅允许相同请求 ID、相同网关凭据、相同会话标识及匹配内容接回。NewAPI 必须覆盖不可信客户端同名头，使用不可预测的唯一 ID，并在这一逻辑请求的重试期间保持它不变。
- 缺少关联条件时记录 `stage=unavailable`，走原处理流程。不能只用共享 API Key、相似提示词或客户端自行填写的用户 ID 关联他人的生成。

**透传请求 ID 本身不保证 Codex 重连能够命中**：如果 NewAPI 对 Codex 每次重新 POST 都生成新的 ID，而且没有已验签用户身份，就无法把两次请求安全地识别为同一任务。

请求业务参数必须相同，重试输入只允许在原输入后附加本任务已完成的消息或推理项。新增用户消息或工具结果属于下一次模型调用。

## TRAE 上游自身断线

另有独立开关，默认关闭：

```yaml
TRAECN_RESUME_UPSTREAM_ENABLED: "1"
```

只有确认部署使用的 `llm_utils_chat` 支持原请求 ID 加 `Last-Event-ID` 续接后再开启。现有抓包不能确认该接口的支持情况；本地测试使用模拟上游验证协议处理。

开启后，网关保存完整上游 SSE 事件的 `id`，流异常结束时最多重连 3 次，携带 `Last-Event-ID`，保持原请求体、两个 TRAE 请求 ID、账号与代理出口。原 Responses 转换器继续处理后续事件，因此正文、推理、工具参数累积状态不会重置。

半截事件不交付，恢复后由上游补发。只允许补发最后一个相同事件一次；重播更早事件、同 ID 内容改变、没有可用游标或重连耗尽都明确失败，不回落到另起一轮生成。若上游忽略游标并用全新的不透明 ID 开始生成，网关无法仅凭 SSE 识别，因此不能用该开关代替对上游协议的验证。

## 思考中途结束与客户端重试

TRAE 返回 `stop` / `done` 时，必须已经产生非空白正文或工具调用，网关才发送 `response.completed`。只有思考摘要、空白正文或完全没有输出时，发送 `response.failed`，错误码为 `upstream_empty_output`，保留上游已报告的用量。失败前不会把未交付的思考项标成完成。

长度截断和内容过滤继续返回 `response.incomplete`，保留原原因；完整正文和有效工具调用正常完成。

| 当前情况 | 网关处理 |
| --- | --- |
| 客户端断线，原任务仍在运行 | 匹配重试接回同一任务 |
| 客户端断线，原任务已成功完成 | 回放尚未确认的输出和成功终态 |
| 尚未派发上游就因账号不可用失败，或生成前被明确鉴权拒绝、限流 | 原任务及订阅结束后，匹配重试自动重新调度 |
| 上游已给出 `response.failed`，且未交付工具调用 | 匹配重试重新调度，客户端直接拿到新生成 |
| 已交付工具调用 | 不接回、不重开，放弃续传保护，按普通流程重新生成 |
| 上游 `cyber_policy` 等明确的内容拒绝 | 不重开（重开只会被再拒一次），放弃续传保护 |
| 静默重开次数用尽（同一逻辑请求 2 次） | 放弃续传保护，按普通流程重新生成 |
| 未完整生成便结束（`response.incomplete` / 缺少终态 / 缓存失败） | 放弃续传保护，按普通流程重新生成 |
| 保留表或输入预算已满（网关自身容量） | 放弃续传保护，按普通流程重新生成 |
| 手动发送“继续”等新消息 | 按新一轮模型调用处理，使用可用历史上下文 |

**续传层不向客户端返回 409。** 它只决定“能不能接回上一条生成”，不决定“这一次请求能不能服务”：接不回就放弃续传保护，让请求走普通流程照常生成。

每次响应带 `X-Codex2API-Resume` 头，取值 `attached`（接回原任务）、`fresh`（首轮新任务）、`restarted`（失败后重新调度的新任务）、`bypass`（放弃续传，按普通流程服务）。

## 失败任务为什么以前会返回 409

409 从来不是额度或账号状态，而是续传层拒绝把“已经跑过一轮生成”的任务重新派发的信号：接回一个已结束的失败任务只能回放失败，重开一轮又可能在客户端留下重复内容。旧实现只把「未派发上游」和「首包前明确 401/429」标记为可重开，其余一律 409，于是出现了“号还有额度，客户端却拿到 409”的情况。

现在的判定只保留两条真正的安全边界：

- **工具调用一旦交付，永不重开**：重开会重新生成一次工具调用，接回会重放已交付的工具项，两者都可能让客户端重复执行同一次调用。
- **上游没有给出失败终态时不重开**：`response.incomplete`、连接断开、超时、缺少终态都无法证明上游没有继续生成，任务内不自动重试；客户端重发时放弃续传保护。

其余情况（上游明确 `response.failed`、生成前被拒、没有可用账号、保留表已满）都直接重新调度或放弃续传，不再把冲突交给客户端。同一逻辑请求最多重新调度 2 次（`traeCNResumeSilentRestartLimit`），用尽后放弃续传保护。

放弃续传的代价是这一轮不再注册续传任务：客户端如果在这一轮中途再次断线，无法接回同一条生成，只会按普通流程重新生成。这类请求也不再受重开次数约束，重试次数由客户端自己决定。上游已交付的工具调用在放弃续传后不会被重放，客户端可能再次执行同一次工具调用。

没有终态的失败（网络断线、超时、未知 5xx、`resume_stream_incomplete`）不会静默重开：这类失败无法证明上游没有继续生成，所以任务内不自动重试。客户端重发时放弃续传保护，按普通流程重新生成。

错误事件能让 Codex 识别失败并自动重试，但无法复活已结束的上游生成。客户端仍可能按自身重试次数再次请求；网关不会反复回放失败流，也不会把新一轮生成伪装成原任务续传。

未生成请求的自动恢复与断线续传不同：HTTP 401 刷新失败后按 `max_retries` 换号，`0` 表示不在本次请求内换号。若预算耗尽或暂时没有可调度账号，仍返回真实失败；客户端重试时可重新调度。替换失败记录须等原后台和订阅均结束，并发重试只创建一个新任务。恢复机制不能修复无效凭据或补充额度。

## 429 与额度不足

- `3004` 携带 `exceeded the rate limit`，以及现有 `4011` 限流，按 429 处理。`Your requests have exceeded the quota.` 识别为额度不足，同样使用 429 重试预算，并在本次请求中排除该账号。不会仅凭未知含义的 `3004` 数字认定限流。
- Responses 尚未发布输出时，按后台 `max_rate_limit_retries` 配置换号；`0` 仍表示不重试。被拒绝尝试的生命周期事件和错误不会写进续传日志，换号后的成功输出仍属于同一个网关任务。
- 思考、正文或工具内容已经开始输出后，同一个任务内不再换号生成；该轮以失败事件结束，客户端重发同一请求时按上面的重新调度规则处理。
- 真实请求和后台测活共用账号冷却，账号显示 `rate_limited`，冷却期间退出新请求调度。该处理独立于普通中转的模型冷却开关。
- 默认限流冷却 60 秒，额度不足冷却 5 分钟。上游 `Retry-After` 或错误里的恢复时间优先，单次提示最多采用 24 小时；后续短限流不会主动缩短已记录的较长冷却。默认时长是临时调度策略，不代表已查到 TRAE 的实际额度重置周期。
- 保留原始错误码和提示；不修改 Codex 的 5 小时、7 天用量窗口，也不把这些业务拒绝当作凭据失效。

## 边界与资源限制

| 项目 | 限制 |
| --- | --- |
| 断开后的保留时间 | 默认 60 秒，可配 1–600 秒 |
| 一次后台任务总时长 | 20 分钟 |
| 每个 Handler 保留的任务 | 最多 64 个，包含完成缓存和短期过期标记 |
| 单次续传请求体 | 最多 16 MiB；输入须为数组，最多 8192 项 |
| 后台运行请求体总预算 | 每个 Handler 64 MiB |
| 每任务事件正文缓存 | 最多 64 MiB，最多 65536 条记录 |
| 全进程事件缓存预算 | 256 MiB，计入记录元数据的预留量 |
| 内存转临时文件阈值 | 每任务 1 MiB，转存后释放正文内存缓冲 |
| 单个 SSE 事件 | 最多 8 MiB |

这些是请求体和事件记录的预算，不等于进程总内存上限；请求转换、上游状态、事件索引及原有上下文缓存还会占用内存。超限时拒绝新任务或终止当前任务，不能驱逐已发出内容后再假装可续传。

缓存只在当前进程有效。多实例部署需要让重试回到同一实例；服务重启、实例切换不支持恢复。正常过期会删除临时文件，进程被强制终止时可能留下 `codex2api-traecn-resume-*` 文件。

工具调用项已发出完成事件后，不再接回原任务：重放工具项可能让客户端重复执行同一次调用，静默重开也会重新生成一次工具调用。这类请求放弃续传保护，按普通流程重新生成。新的工具结果请求仍按下一轮调用处理。

过期并且原任务收尾后，额外保留一个保留期的失败标记。迟到重试不再拿到 409：它会放弃续传保护、按普通流程重新生成。失败标记也过期后，同样输入同样按新请求处理；客户端不应无限自动重试旧请求。

## 日志与验证

- `[RESPONSES-IDENTITY]`：每次 HTTP 入口及结束的网关请求 ID、NewAPI 请求 ID、会话标识和断开状态；`requested_channel` 是 Key 限定的渠道，`resume_enabled` 是任务保留开关。
- `[TRAECN] stage=terminal`：实际发送的终态 `event`、上游 `finish_reason`、错误或截断 `reason`，以及思考、正文长度和工具数量。
- `[TRAECN] stage=cooldown`：进入冷却的账号、`rate_limited` / `usage_limit` 原因与冷却秒数。
- `[TRAE-RESUME] stage=attach`：`created=true` 是新任务；`created=false` 是接回，`task` 应保持相同。
- `stage=detach` / `stage=expired`：连接解除订阅、任务过期。
- `stage=worker_done`：原任务结束时的 `terminal_event`、`terminal_code` 和本地 `failure`；HTTP 200 或空 `failure` 不能单独证明生成成功。
- `stage=refuse`：续传层拒绝接回原任务，记录原因、原终态与错误码；紧随其后是 `stage=bypass`。
- `stage=retry`：失败记录被替换，`terminal_event` 与 `silent_restarts` 说明这是第几次重新调度；随后 `stage=attach created=true` 启动新的调度。
- `stage=bypass reason=…`：放弃续传保护、按普通流程服务这次请求，同时打印当前 `tasks` 与 `input_bytes`。
- `stage=upstream_reconnect`：实际向 TRAE 重连的原请求 ID 和事件游标。

日志不输出凭据或提示词正文。接回时用量由原后台任务完成一次处理；NewAPI 自身对断开请求和重试请求的记账仍须按其配置验证。

本地测试覆盖真实 HTTP 客户端断开、持续重试开启时实时输出、同任务接回、已确认消息和推理去重、共享 Key 身份隔离、过期取消、缓存落盘与预算释放，以及模拟 TRAE 的游标恢复和错误游标处理。

2026-09-15 使用本机 Codex 后端 `0.154.0-alpha.6.2`，串联模拟 NewAPI、实际网关处理器和模拟 TRAE 强制断流验证：Codex 自动重连一次、同一后台任务接回、最终正文完整、模拟 TRAE 只生成一次。该验证不代表真实 `llm_utils_chat` 已支持上游游标续传。

同一客户端的终态实验确认：只有思考项的 `response.completed` 会直接结束本轮，没有重试。修复后的实际网关在这一场景发出 `upstream_empty_output`；按当前默认策略，Codex 自动重试时会静默重开一轮（`X-Codex2API-Resume: restarted`），不再把 409 交给客户端，也不再产生 `turn.failed`。正常断线接回的完整输出回归仍通过。

Windows / Go 1.26.6 回归检查中，5 个现有临时文件测试失败，使用本地 HTTP/2 测试辅助函数的一组测试因空指针崩溃；修改前编译的测试程序可复现这些问题。跳过崩溃组后，其余 proxy 测试执行完成，失败仍为上述 5 项。新增续传测试与 `go vet ./...` 通过。
